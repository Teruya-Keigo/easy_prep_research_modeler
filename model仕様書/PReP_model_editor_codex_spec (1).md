# PRePモデルエディタ MVP 実装仕様書

仕様版：v1.3.0（完成済みv1.2.1への差分改訂。保存スキーマはv1.3.0）

## 0. この仕様書の使い方

この文書は、Codex に渡してそのまま実装を開始できる粒度で、PRePモデルを自作するための小規模なWebエディタを定義したものである。

実装対象は、既存の PReP Studio の完全な再現ではない。今回の研究で必要な次の作業を、短時間で行えることを目的とする。

- PRePモデルを新規作成する
- 複数のプロセスと、各プロセス内のサブプロセスを定義する
- 1つのプロセスを、アクター別の横レーンとサブプロセス別の縦列で編集する
- 各成果物の責任アクターを明示する
- 入力関係と同期関係を結ぶ
- 成果物の上下左右と四隅の8方向から関係線を結ぶ
- 複数プロセスの関係を鳥瞰図で確認する
- 研究用の意味関係を付与する
- 成果物の状態と属性を記録する
- 保証連鎖と変更影響を確認する
- タッチパッドの二本指ドラッグでキャンバスを縦横に移動する
- サブプロセスの範囲ボックスの幅と高さを自由に変更する
- モデルを保存、復元、画像出力する

この仕様書の最後に、Codexへそのまま渡す実装依頼文を記載する。

## 1. 作成するツール

### 1.1 仮称

**PReP Research Modeler**

### 1.2 一文説明

PRePの成果物中心記法に基づいて、プロセスゴール、成果物、成果物間関係を視覚的に編集し、保証連鎖と変更影響を確認できる、ブラウザ完結型の研究用モデルエディタである。

### 1.3 想定利用者

- PRePを用いて研究プロセスやテスト設計プロセスを記述する研究者
- 今回の研究で、制約付き多ラベル分類システムのテスト設計モデルを作成する本人

### 1.4 初版の到達点

初版では、以下を満たせば完成とする。

1. ゼロからモデルを作成できる
2. PRePの4種類の成果物を配置できる
3. プロセス内にサブプロセスを作成し、階層を編集できる
4. アクターを作成し、各成果物へ責任アクターを割り当てられる
5. アクターを横レーン、直下のサブプロセスを縦列として表示できる
6. 1つのプロセス編集画面に、別のトップレベルプロセスの詳細を混在させない
7. 入力関係と同期関係を描ける
8. 各成果物の上下左右と四隅にある8個の接続点を利用できる
9. 複数プロセスを二重丸で表示する鳥瞰図を作成できる
10. 成果物の状態、属性、説明、内外区分を編集できる
11. 研究用の6種類の意味関係を関係線に付与できる
12. モデルの妥当性を検査できる
13. 保証連鎖と変更影響をハイライトできる
14. JSONによる保存・読込ができる
15. PNGまたはSVGで図を出力できる
16. 「制約付き多ラベル分類システムのテスト設計」テンプレートを読み込める
17. プロセス詳細と鳥瞰図の両キャンバスを、タッチパッドの二本指ドラッグで縦横に移動できる
18. サブプロセスの範囲ボックスをドラッグまたは数値入力で任意の幅・高さへ変更し、保存・復元できる

### 1.5 v1.2／v1.2.1／v1.3.0の変更点

完成済みのv1.1に対する修正要件として、編集単位、責任分担、接続点、鳥瞰図を追加する。v1.2.1ではキャンバス操作を追加した。v1.3.0ではサブプロセスの範囲ボックスの高さを保存対象に追加し、幅と高さを個別に変更できるようにする。

| 項目 | 決定 |
|---|---|
| 編集単位 | 詳細編集画面では、選択中の1プロセスだけを操作する |
| サブプロセス | 選択中プロセスの直下のサブプロセスを縦方向の列として並べる |
| アクター | 選択中プロセスに参加するアクターを横方向のレーンとして並べる |
| 成果物の配置 | 「責任アクターのレーン」と「所属サブプロセスの列」の交点に配置する |
| 成果物の責任 | 各成果物は1人の主責任アクターを必須で持つ。補助担当は初版対象外とする |
| 接続点 | 上、右上、右、右下、下、左下、左、左上の8個を持つ |
| 複数プロセス | 別画面の鳥瞰図で、各トップレベルプロセスを二重丸として表示する |
| プロセス間連携 | 鳥瞰図の引継ぎ線として管理し、詳細画面をまたぐ長い成果物線は描かない |
| タッチパッド操作 | 二本指ドラッグの縦・横移動量でキャンバスを自由方向へパンする。ピンチ操作はズームとして維持する |
| サブプロセス範囲 | 各サブプロセスを幅・高さを個別変更できる矩形ボックスとして表示し、サイズを保存する |
| 保存形式 | `schemaVersion = 1.3.0` とし、v1.0.0、v1.1.0、v1.2.0を移行読込する |

サブプロセスの再帰的な親子関係は維持する。ただし、1画面に表示するのは選択中プロセスとその直下の子だけとする。さらに深い階層は、対象サブプロセスを開いて別の詳細画面として編集する。これにより、階層を保持しながら「1画面＝1プロセス」を崩さない。

## 2. 情報源から固定した設計原則

### 2.1 成果物中心で記述する

PRePは、処理手順ではなく、業務の目的から見た意味的なまとまりである成果物を中心にプロセスを記述する。

したがって、初版ではタスク、分岐、イベントを中心にしたBPMN風エディタにはしない。キャンバス上の主役は成果物とその関係である。

根拠：

- `EA演習（Day02）.pdf`, pp.24-32：タスク視点と成果物視点の比較
- `EA演習（Day02）.pdf`, pp.35-39：成果物を「業務の目的的観点から見た意味的なまとまり」「管理されているもの」と定義
- `01-prep_goal_reframed.md`, §3：テスト設計研究を成果物ネットワークとして扱う方針

### 2.2 PReP標準の線種と研究用意味関係を分離する

講義資料で示される成果物間関係は、次の2種類である。

| PReP標準関係 | 表示 | 意味 |
|---|---|---|
| 入力関係 | 実線・有向 | 入力元から入力先へパラメータ値が入力される |
| 同期関係 | 点線・双方向 | 両成果物のパラメータ値が相互に関係して決定される |

一方、研究メモでは、保証連鎖や変更影響を表す6種類の関係が定義されている。

- `derives-from`
- `justifies`
- `mitigates`
- `approves`
- `monitors`
- `requires-revalidation-of`

これらを同じ列挙型へ混在させると、PReP標準記法と研究上の拡張を区別できなくなる。そのため、関係データは次の2階層で保持する。

- `prepType`: PReP標準の線種
- `semanticType`: 研究上の意味ラベル

根拠：

- `EA演習（Day02）.pdf`, p.41：入力関係と同期関係
- `02-prep_research_reframed_plan.md`, §7, §14.4：研究で用いる6種類の関係

### 2.3 成果物の種類を見た目で区別する

成果物は次の4種類を持つ。

| 種類 | 用途 | 表示規則 |
|---|---|---|
| 中間成果物 | プロセス内部で生成・利用される通常成果物 | 実線枠、白背景 |
| 最終成果物 | 対象プロセス外へ出力される成果物 | 実線枠、灰色背景 |
| マイルストーン成果物 | 品質管理ゲート、確認・承認、チェックポイント | 実線枠、上部に青い帯 |
| 無実体成果物 | 判断・知見など、管理されていない状態の成果物 | 点線枠、白背景 |

根拠：

- `EA演習（Day02）.pdf`, p.40：4種類の成果物と定義
- `04-PReP-.md`, §6.1-6.2：サブゴールとマイルストーン成果物の対応

### 2.4 成果物の状態は時系列ではなく質的変化として扱う

成果物の状態は、時間の経過ではなく、別の成果物が入力されることによる情報の質的変化を表す。

したがって、状態は自由記述の単一フィールドに限定せず、同一成果物について複数の状態を並べられる構造にする。ただし初版UIでは、ノード右側のプロパティ欄で状態を追加・削除する簡易操作でよい。

根拠：

- `EA演習（Day02）.pdf`, p.42：成果物の状態の定義

### 2.5 システム、プロセス、サブプロセス、成果物の階層を持つ

モデル全体にはシステム名とシステムゴールがあり、システムは1つ以上のプロセスから構成され、プロセスは1つ以上の成果物を持つ。

完成済み初版への追加要件として、プロセスは0個以上のサブプロセスを持てるものとする。サブプロセスは別のノード種別を増やして表現するのではなく、`PrepProcess` の親子関係で表現する。`parentProcessId` を持たないプロセスはシステム直下のトップレベルプロセス、持つプロセスは指定された親プロセス内のサブプロセスである。

```text
システム
└── プロセス
    ├── 成果物
    └── サブプロセス
        ├── 成果物
        └── サブプロセス
```

資料が明示している標準階層は「システム → プロセス → 成果物」である。サブプロセス階層は、プロセスを詳細化して管理するための本ツール上の拡張であり、PReP標準の新しい記号として扱わない。

処理モデルの詳細はPRePモデルから切り離す。初版でタスクフロー、業務ロジック、BPMNイベントを実装しない理由はここにある。

根拠：

- `EA演習（Day02）.pdf`, p.43：システム、プロセス、成果物、処理モデルの基本構成
- `EA演習（Day03）.pdf`, p.6：プロセスゴール、要求、出力、入力先プロセスの基本構造
- ユーザ修正要件：プロセス内にサブプロセスを作成する

### 2.6 リスク分析、As-is、To-beをモデルの表示モードとして扱う

リスク分析では、無実体成果物や同期関係など、点線で表現される箇所に潜在リスクが存在するという考え方が示されている。また、As-isモデルから問題箇所を分析し、To-beモデルとシステム要件へ接続する流れが示されている。

初版では完全なAs-is/To-be差分管理は行わないが、次の属性と表示機能を設ける。

- モデルの `phase`: `as-is | to-be | unspecified`
- 成果物または関係の `riskLevel`: `none | low | medium | high`
- リスク表示モード：リスクがある要素だけを強調

根拠：

- `EA演習（Day02）.pdf`, pp.45-47：リスクの可視化、原因分析、As-isからTo-beへの改善
- `EA演習（Day04）.pdf`, pp.8-15：As-isモデル、リスク分析、To-be設計、システム追加

### 2.7 プロセス詳細はアクターとサブプロセスの直交表として表す

プロセス詳細画面は、次の直交構造で表す。

- 横方向のレーン（行）：アクター
- 縦方向の区画（列）：選択中プロセスの直下のサブプロセス
- 行と列の交点：そのアクターが責任を持ち、そのサブプロセスに属する成果物

アクターのレーンは上から下へ並ぶ「水平な帯」であり、サブプロセスは左から右へ並ぶ「垂直な列」である。単なる背景装飾ではなく、成果物の責任と所属を決める編集上の制約として扱う。

各サブプロセス列は、そのサブプロセスが占める範囲を示す矩形ボックスとして描画する。ボックスの幅と高さはサブプロセスごとに独立して変更できる。幅を変えた場合は後続列の開始位置を再計算し、重なりを作らない。高さを変えた場合もアクターの横レーン自体は維持し、ボックスとレーンが交差する領域だけを成果物の配置可能セルとする。

成果物を別の横レーンへ移動すると `responsibleActorId` が変わる。別の縦列へ移動すると、その列に対応するサブプロセスへ `processId` が変わる。両方をまたいで移動した場合は、責任アクターと所属サブプロセスを同時に更新する。

根拠：

- `EA演習（Day02）.pdf`, p.34：業務鳥瞰図と業務プロセス図を分離し、業務プロセス図内でアクターと工程を構造化している
- ユーザ修正要件：アクターを横レーン、サブプロセスを縦方向に配置し、各成果物の責任を明示する
- ユーザ追加要件：サブプロセスの範囲ボックスの大きさを自由に変更できるようにする

### 2.8 1つの詳細画面では1つのプロセスだけを編集する

トップレベルプロセスが複数あっても、それらの成果物を同じ詳細キャンバスへ同時表示しない。詳細画面は必ず `activeProcessId` を1つ持ち、そのプロセスと直下のサブプロセス、参加アクター、成果物、成果物間関係だけを表示する。

別プロセスへの移動は、次のいずれかで行う。

- 上部のプロセス選択欄
- パンくず
- 鳥瞰図の二重丸をダブルクリック
- サブプロセス列の「このサブプロセスを開く」

この制約により、複数プロセスの内部構造が同じキャンバスで重なり、どのプロセスを操作しているか分からなくなることを防ぐ。

根拠：

- `EA演習（Day02）.pdf`, p.34：業務鳥瞰図と各業務の業務プロセス図を別のモデルとして扱う構成
- ユーザ修正要件：一つの画面では基本的に一つのプロセスを操作する

### 2.9 複数プロセスの関係は鳥瞰図で表す

鳥瞰図は、プロセス内部の成果物構造ではなく、トップレベルプロセス同士の関係を確認する画面である。各プロセスは二重丸で表し、プロセス間の成果物引継ぎを矢印で結ぶ。

鳥瞰図の線は、成果物同士の `PrepRelation` とは別の `ProcessHandoff` として保持する。詳細画面をまたぐ成果物線を無理に1本のキャンバスへ描かない。`ProcessHandoff` には、引継ぎ対象の最終成果物と、必要な場合は受け側の外部入力成果物を対応付ける。

根拠：

- `EA演習（Day02）.pdf`, p.34：業務領域と業務の定義を行う「業務鳥瞰図」と、各業務の詳細を表す「業務プロセス図」の分離
- ユーザ修正要件：複数プロセスが複雑に関係する場合は鳥瞰図を作り、各プロセスを二重丸で表現する

## 3. 初版で実装しないもの

短期間で完成させるため、以下は初版の対象外とする。

- ユーザアカウント
- クラウド保存
- 同時共同編集
- コメント、承認ワークフロー
- BPMNファイルのインポート・変換
- PReP Studio独自ファイルとの互換性
- IPM作成
- 制約充足判定
- 組み合わせテストケース生成
- テストスイート選定
- 実テスト実行
- 自然言語からのモデル自動生成
- 完全なAs-is/To-be差分管理
- サブプロセスをBPMNの実行可能なサブプロセスへ変換する機能
- サブプロセスごとに別ファイルへ分割して保存する機能
- 1成果物に複数の主責任アクターを割り当てる機能
- アクター間のRACIマトリクス
- 1つの詳細画面へ複数のトップレベルプロセスを展開する機能
- 鳥瞰図上で成果物の内部状態を直接編集する機能

`05-tool_and_reducible_artifacts_summary.md` に記載されたIPM作成、制約検査、テストケース生成、選定支援は、PRePモデルを利用する後続のドメインツールである。本エディタ初版へ混在させない。

## 4. 画面構成

### 4.1 画面モード

画面は、責務の異なる次の2モードに分ける。

| モード | 目的 | 主な表示要素 |
|---|---|---|
| プロセス詳細 | 1つのプロセス内部を編集する | アクター横レーン、サブプロセス縦列、成果物、成果物間関係 |
| 鳥瞰図 | 複数のトップレベルプロセスの関係を編集する | 二重丸のプロセス、プロセス間引継ぎ線 |

`EditorViewState.mode` は `process | overview` とする。`process` の場合は `activeProcessId` を必須とする。ページ遷移を伴うルーティングでも、同一SPA内のモード切替でもよいが、同じキャンバスへ両モードのノードを混在させない。

起動時の規則：

- トップレベルプロセスが1件なら、そのプロセス詳細を開く
- トップレベルプロセスが2件以上なら、前回の表示状態を復元する。履歴がなければ鳥瞰図を開く
- 読込データに `lastView` がなくてもモデル本体は正常に開ける

### 4.2 共通レイアウト

デスクトップ利用を優先し、次の3カラム構成とする。

| 領域 | 幅の目安 | 内容 |
|---|---:|---|
| 左サイドバー | 240px | 要素追加、プロセス一覧、テンプレート、表示モード |
| 中央キャンバス | 可変 | プロセス詳細または鳥瞰図 |
| 右プロパティ | 320px | 選択要素の編集、検証結果 |

画面上部に共通ツールバーを置く。狭い画面では右プロパティをドロワーにしてよいが、キャンバスの編集可能幅を最低800px確保する。

### 4.3 上部ツールバー

左から次の操作を配置する。

- 鳥瞰図へ戻る／プロセスを開く
- 現在のプロセス名または「鳥瞰図」
- プロセス選択
- パンくず
- 元に戻す
- やり直す
- 自動整列
- 検証
- 保証連鎖
- 変更影響
- JSON読込
- JSON保存
- PNG出力
- SVG出力

モデル名と保存状態も表示する。保証連鎖と変更影響はプロセス詳細モードだけで有効にする。画像出力は現在のモードだけを対象とし、プロセス詳細では現在の1プロセス、鳥瞰図では鳥瞰図全体を出力する。

### 4.4 左サイドバー

#### プロセス詳細モード

- アクター追加
- サブプロセス追加
- 中間成果物
- 最終成果物
- マイルストーン成果物
- 無実体成果物
- アクター一覧
- サブプロセス一覧
- 通常／リスク／保証連鎖／変更影響の表示切替

成果物はパレットから任意のセルへドラッグして追加する。ドロップ先の行から責任アクター、列から所属サブプロセスを自動設定する。セル外へドロップした場合は追加せず、配置先を選ぶよう案内する。

#### 鳥瞰図モード

- トップレベルプロセス追加
- 外部プロセス追加
- プロセス一覧
- プロセス間引継ぎ追加

サブプロセスは鳥瞰図へ個別表示しない。二重丸として表示する対象は `parentProcessId` を持たないトップレベルプロセスである。

#### テンプレート

- 空のモデル
- 制約付き多ラベル分類システムのテスト設計
- コーヒーを淹れるプロセス

初版で完全な内容が必要なのは、最初の2つである。コーヒー例は最小の動作確認用でよい。

### 4.5 プロセス詳細キャンバス

#### 4.5.1 グリッド構成

上端にサブプロセス見出し、左端にアクター見出しを固定し、中央を次のグリッドにする。

```text
                        サブプロセスA     サブプロセスB     サブプロセスC
アクター1の横レーン      成果物            成果物
アクター2の横レーン                        成果物            成果物
アクター3の横レーン      成果物                              成果物
```

- アクターは上から下へ並ぶ水平レーン
- サブプロセスは左から右へ並ぶ、独立した範囲ボックスを持つ垂直列
- 成果物は必ず1つの交点セルに所属する
- レーン高さとサブプロセス範囲ボックスの幅・高さはユーザが変更でき、順序とサイズを保存する
- 見出しはスクロール時も表示する
- 直下のサブプロセスが0件の場合は「サブプロセスを追加してください」と表示する

選択中プロセス自身に直接属し、サブプロセスに未分類の既存成果物は、移行用の「未分類」列へ表示する。「未分類」は保存上のサブプロセスではなく、`artifact.processId === activeProcessId` を表すビュー上の列である。新規成果物は原則として実サブプロセス列へ作成する。

#### 4.5.2 操作

- 成果物ノードの移動
- 複数選択
- Deleteキーによる削除
- 8方向の接続点ドラッグによる関係作成
- ズーム
- パン（マウスドラッグ、Space＋ドラッグ、タッチパッドの二本指ドラッグ）
- 全体表示
- ミニマップ
- スナップグリッド
- アクターレーンの並べ替えと高さ変更
- サブプロセス列の並べ替えと範囲ボックスの幅・高さ変更
- サブプロセス列からそのサブプロセス詳細を開く
- 選択中プロセスまでの階層を示すパンくず

成果物を別セルへドラッグした場合は、次の規則でドメインデータを更新する。

| 移動 | 更新 |
|---|---|
| 同じ列で別レーン | `responsibleActorId` を変更 |
| 同じレーンで別列 | `processId` を移動先サブプロセスIDへ変更 |
| 別レーン・別列 | 両方を変更 |
| セル外 | 元の配置へ戻す |

プロセスを別プロセス内へ移動する階層編集は、キャンバス上の自由ドラッグではなく、右パネルの親プロセス変更または鳥瞰図上の専用操作で行う。自分自身または自分の子孫を親には指定できない。

#### 4.5.3 サブプロセス範囲ボックスのリサイズ

サブプロセス範囲ボックスを選択すると、右辺、下辺、右下角にリサイズハンドルを表示する。ドラッグ操作で幅だけ、高さだけ、または幅と高さを同時に変更できる。右プロパティパネルの数値入力でも同じ値を編集できる。

- 新規サブプロセスの幅は360px、高さは `auto` とする
- `auto` 高さは現在の全アクターレーンの合計高に一致させる
- 初めて高さをドラッグまたは数値入力した時点で手動高さへ切り替える
- 手動高さは160px以上、幅は260px以上とする
- 幅変更時は後続のサブプロセス列を左右へ移動し、範囲ボックス同士を重ねない
- 高さ変更ではほかのサブプロセスの高さを変更しない
- ボックス内の成果物の位置と大きさは拡大縮小しない
- 縮小限界は、ボックス内の最も右または下にある成果物の外周＋24pxとする
- 縮小操作が限界を超えた場合は限界値で止め、成果物を範囲外へ押し出したり別サブプロセスへ移したりしない
- リサイズ後は関係線を再計算するが、`sourceAnchor` と `targetAnchor` は変えない
- 連続したドラッグはUndo履歴上の1操作として扱う
- リサイズ中はキャンバスのパン、成果物ドラッグ、関係作成を開始しない
- ダブルクリックまたは右パネルの「高さを自動に戻す」で `auto` 高さへ戻せる

成果物の所属判定には成果物ノードの中心点を使用する。中心点がサブプロセス範囲ボックスとアクターレーンの交差領域に入っている場合だけ、そのセルへの配置を有効とする。リサイズによって既存成果物の中心点が範囲外になる操作は許可しない。

#### 4.5.4 タッチパッドによる縦横パン

プロセス詳細キャンバスと鳥瞰図キャンバスの両方で、ポインタがキャンバス上にある間のタッチパッド二本指ドラッグをキャンバスのパンとして扱う。

- 上下方向の操作はビューポートの `y` を更新する
- 左右方向の操作はビューポートの `x` を更新する
- 斜め方向の操作は `x` と `y` を同時に更新し、縦横どちらかへ固定しない
- 二本指ピンチはズームとして扱い、二本指ドラッグによるパンと区別する
- `Meta`（macOS）または `Control`（Windows/Linux）を押しながらのスクロールはズームとして利用できる
- キャンバス上でパンを処理したときはページ本体をスクロールさせない
- ノード、接続点、レーン見出し、列見出しのドラッグ中は、それぞれの編集操作を優先し、同じ入力でキャンバスをパンしない
- パン操作では成果物座標、責任アクター、所属サブプロセス、選択状態を変更しない
- 操作終了後のビューポート `x`、`y`、`zoom` は既存の `ViewportState` として保存する

`ProcessCanvas` と `OverviewCanvas` の `<ReactFlow />` には、原則として次を共通設定する。

```tsx
<ReactFlow
  panOnScroll
  panOnScrollMode="free"
  panOnScrollSpeed={0.5}
  zoomOnPinch
  preventScrolling
  onMoveEnd={handleViewportChange}
  {...otherProps}
/>
```

`panOnScrollMode="free"` により、タッチパッドが送る横方向と縦方向のスクロール量を両方パンへ使う。ピンチおよび修飾キー付きスクロールのズームが利用中の `@xyflow/react` バージョンで期待どおり動くことを実機確認する。標準propsで満たせる限り、独自の `wheel` イベントハンドラは追加しない。やむを得ず補助ハンドラを追加する場合も、`preventDefault()` はキャンバス要素内かつ実際にパンまたはズームを処理したイベントだけに限定し、リスナーを `passive: false` で登録・確実に解除する。

この設定は、React Flow公式のデザインツール型ビューポート操作と、`panOnScroll`、`panOnScrollMode`、`zoomOnPinch`、`preventScrolling` の仕様に従う。

#### 4.5.5 関係作成

成果物ノードは次の8接続点を持つ。

| ID | 位置 |
|---|---|
| `n` | 上中央 |
| `ne` | 右上角 |
| `e` | 右中央 |
| `se` | 右下角 |
| `s` | 下中央 |
| `sw` | 左下角 |
| `w` | 左中央 |
| `nw` | 左上角 |

各接続点は入力・出力の両方に使えるよう、React Flowの `connectionMode="Loose"` を利用する。接続点ごとに一意なIDを付け、関係の `sourceAnchor` と `targetAnchor` へ保存する。ノード未選択時は接続点を薄くし、ホバー時または選択時に明瞭に表示する。見た目の円は8px程度、操作判定領域は16px以上とする。

React Flowの経路計算へ渡す方向は、`n = Top`、`s = Bottom`、`e/ne/se = Right`、`w/nw/sw = Left` とする。四隅の実座標はCSSで角へ置き、経路の初期進行方向だけをこの規則で固定する。これにより、角へ接続した線がノード内部へ戻ることを防ぐ。

接続後に関係作成ダイアログを開き、次を選択する。

1. PReP標準関係
   - 入力関係
   - 同期関係
2. 研究用意味ラベル
   - なし
   - `derives-from`
   - `justifies`
   - `mitigates`
   - `approves`
   - `monitors`
   - `requires-revalidation-of`
3. 始点接続点
4. 終点接続点
5. 説明

関係線は `smoothstep` を初期値とする。線を選択した後、始点または終点の接続点を右パネルから変更できる。同一接続点へ複数の線を結ぶことを許可する。

### 4.6 鳥瞰図キャンバス

鳥瞰図には、トップレベルプロセスと外部プロセスだけを表示する。

- トップレベルプロセス：二重丸
- 外部プロセス：点線の二重丸
- プロセス間引継ぎ：有向矢印
- 同期的なプロセス間関係：点線の双方向矢印

二重丸は、外円と内円の間隔を6px以上取り、縮小時も単なる太い一重丸に見えないようにする。円内にプロセス名を表示し、長い名称は2行まで折り返す。

操作：

- 二重丸の移動
- 8方向の接続点を用いた引継ぎ線作成
- ダブルクリックまたはEnterでプロセス詳細を開く
- トップレベルプロセスの新規作成、複製、削除
- プロセス間引継ぎの作成、編集、削除
- 自動整列、ズーム、パン（タッチパッドの二本指ドラッグを含む）、全体表示、ミニマップ

鳥瞰図で引継ぎ線を作成した場合は、次を入力する。

- 引継ぎ元プロセス
- 引継ぎ先プロセス
- 引継ぎ対象の最終成果物（0件以上）
- 対応する受け側成果物（0件以上）
- 入力関係または同期関係
- 説明

最終成果物が未作成でも、プロセス間の関係を先に置けるよう `artifactIds` は0件を許可する。ただし警告を出す。

## 5. 視覚表現

### 5.1 成果物ノード

共通仕様：

- 角丸矩形
- 上段：名称
- 下段：現在状態
- 下端：成果物であることを示す短い水平線
- 上下左右と四隅に8個の接続点
- 選択時は青いアウトライン
- リスクレベルが高い場合は右上に警告アイコン

種類別仕様：

```text
中間成果物：
  border: 1.5px solid #374151
  background: #ffffff

最終成果物：
  border: 1.5px solid #111827
  background: #e5e7eb

マイルストーン成果物：
  border: 1.5px solid #2563eb
  background: #ffffff
  header: #dbeafe

無実体成果物：
  border: 1.5px dashed #6b7280
  background: #ffffff
```

### 5.2 アクターレーン

- 水平方向にキャンバス全幅へ伸びる帯
- 左端にアクター名と役割
- レーン間を1pxの水平線で区切る
- 奇数行と偶数行でごく薄く背景色を変える
- 選択時は左見出しだけを強調し、成果物の色と競合させない
- 高さの初期値は220px、最小160px

### 5.3 サブプロセス列

- アクター横レーン上に重ねる矩形の範囲ボックス
- 上端にサブプロセス名とゴール
- 列間を1.5pxの縦線で区切る
- 選択時は上見出しと範囲ボックスの外枠を強調する
- 幅の初期値は360px、最小260px
- 高さの初期値は `auto`（全アクターレーンの合計高）、手動設定時の最小値は160px
- 選択時は右辺、下辺、右下角にリサイズハンドルを表示する
- 列見出しに「開く」ボタンを置き、選択したサブプロセスを次の詳細画面として開ける

アクターレーンとサブプロセス列はReact Flowのグループノードとして自由に重ねるのではなく、レイアウト層で生成する制約付きグリッドとする。成果物ノードと関係線だけをReact Flowの編集対象にし、レーン・列の並べ替えや範囲ボックスのリサイズ時にセル矩形を再計算する。サブプロセス範囲ボックスは互いに重ねず、左から右への列順序を維持する。

### 5.4 鳥瞰図のプロセス

トップレベルプロセス：

- 外円と内円を持つ二重丸
- 外径112px以上、内円との間隔6px以上
- 中央にプロセス名
- 選択時は外円を青くする
- 8方向の接続点を持つ
- ダブルクリックで詳細画面を開く

外部プロセス：

- 点線の二重丸
- 名称のみ表示
- 詳細画面は持たない

サブプロセスは鳥瞰図へ表示しない。鳥瞰図の二重丸と、プロセス詳細画面のサブプロセス列を同じ記号として扱わない。

### 5.5 関係線

| 関係 | 線 | 矢印 | ラベル |
|---|---|---|---|
| 入力関係 | 実線 | 入力先側に1つ | `semanticType` がある場合のみ中央表示 |
| 同期関係 | 点線 | 両端 | `semanticType` がある場合のみ中央表示 |
| プロセス間引継ぎ | 実線 | 引継ぎ先側に1つ | 引継ぎ成果物名。複数の場合は件数 |
| プロセス間同期 | 点線 | 両端 | 説明がある場合のみ表示 |

リスク表示モードでは、`medium` は橙、`high` は赤で線を強調する。

接続点が角の場合も、線がノード内部を横切らないよう始点方向と終点方向をルーティングへ渡す。線の交差が避けられない場合でも、端点位置はユーザが選んだ接続点から動かさない。

```ts
  processes: PrepProcess[];
  actors: PrepActor[];
  processActorLanes: ProcessActorLane[];
  artifacts: PrepArtifact[];
  externalProcesses: ExternalProcess[];
  relations: PrepRelation[];
  processHandoffs: ProcessHandoff[];
  layout: {
    processViews: ProcessViewLayout[];
    overview: OverviewLayout;
    lastView?: EditorViewState;
  };
}
```

### 6.2 保存形式の方針

- 拡張子は `.prep.json`
- UTF-8
- JSONは2スペースインデント
- `schemaVersion` を必須とする
- 新規保存時の `schemaVersion` は `1.3.0` とする
- `1.0.0` は、全プロセスの `parentProcessId` を未指定としてv1.1相当へ変換してからv1.2へ移行し、最後にv1.3へ移行する
- `1.2.0` の `SubprocessColumnLayout` は `height` 未指定のまま読み込み、全アクターレーンの合計高に追従する `auto` 高さとして扱う
- `1.1.0` の `responsibleActor` 文字列は、同一名称ごとに1件の `PrepActor` へ変換する
- 責任主体が空の旧成果物は、`isPlaceholder = true` の「未割当」アクターへ一時配置し、`E015` を表示する
- 旧 `nextProcessName` は同名のトップレベルプロセスが1件だけ存在する場合に `ProcessHandoff` へ変換する。解決できない場合は `legacyNextProcessName` に保持して `W017` を表示する
- 旧関係の接続点は `sourceAnchor = auto`、`targetAnchor = auto` として読み込み、最初の編集または再保存時に最寄りの8方向へ確定できる
- 旧ノード座標から、トップレベルプロセスは鳥瞰図座標、成果物は該当セル内の相対座標へ変換する
- 旧プロセス内の直下サブプロセスは、x座標の昇順で縦列順序を作る
- 旧責任主体の出現順からアクターレーン順序を作る
- 未知の将来フィールドは読込時に無視する
- 必須フィールド欠落時は、壊れた状態で読まずエラー一覧を表示する
- ブラウザの `localStorage` に5秒以内のデバウンスで自動保存する
- 明示的なJSON保存はブラウザからファイルをダウンロードする
- プロセス階層、アクター、レーン順序、列順序、サブプロセス範囲ボックスの幅・手動高さ、セル内座標、8方向の接続点、鳥瞰図座標を保存・復元する

### 6.3 プロセス階層の整合性

- 親プロセスは同一モデル内に存在しなければならない
- プロセスは自分自身を親にできない
- 祖先と子孫が循環する階層を作れない
- 成果物の `processId` は、同一モデル内のプロセスまたはサブプロセスを参照する
- 成果物の `responsibleActorId` は、同一モデル内のアクターを参照する
- プロセス詳細画面に表示するサブプロセスは、`parentProcessId === activeProcessId` を満たす直下の子だけとする
- ある成果物を親プロセスPの画面に表示できるのは、`artifact.processId === P` または `artifact.processId` がPの直下の子である場合だけとする
- `ProcessActorLane.processId` と `actorId` の組は重複させない
- 同じプロセス内のレーン `order` と、同じ親配下の列 `order` は一意に正規化する
- サブプロセス範囲ボックスの `width` は260px以上、手動 `height` は160px以上の有限数とする
- 関係の端点IDは階層によらず常に実体の要素IDを保持する
- 成果物間関係は、同じ詳細画面へ表示可能な成果物同士に限定する。トップレベルプロセスをまたぐ関係は `ProcessHandoff` を使う
- `ProcessHandoff` の始点と終点は異なるトップレベルプロセスでなければならない
- `ProcessHandoff.sourceArtifactIds` は始点プロセス配下の最終成果物だけを参照する
- `ProcessHandoff.targetArtifactIds` は終点プロセス配下の外部入力成果物だけを参照する
- `sourceAnchor` と `targetAnchor` は定義済みの8方向または移行用の `auto` でなければならない
- プロセス削除時、子要素が存在する場合は即時削除しない。「子要素を親へ移す」または「配下を含めて削除」を確認ダイアログで選ばせる
- アクター削除時、責任成果物が存在する場合は即時削除せず、移管先アクターを選ばせる

React Flowはノード・エッジ・ビューポートをJSON互換形式として保存できるため、編集状態の保存・復元に適している。ただし、ドメインモデルをReact Flowの内部表現へ直接依存させず、上記 `PrepModelFile` を正とする。技術的な保存・復元方法は [React Flow公式のSave and Restore](https://reactflow.dev/examples/interaction/save-and-restore) と [ReactFlowJsonObject](https://reactflow.dev/api-reference/types/react-flow-json-object) を参照する。

## 8. 保証連鎖表示

### 8.1 目的

研究で固定された保証連鎖を、キャンバス上で追跡できるようにする。

基本形：

```text
信頼性要求
  → 制約定義
  → テストケース集合
  → 評価基準
  → 評価結果
  → 残余リスク評価
  → 引継ぎ条件
```

根拠：

- `02-prep_research_reframed_plan.md`, §8：保証連鎖の定義

### 8.2 操作

1. ユーザが成果物を1つ選択する
2. 「保証連鎖」を押す
3. 選択成果物から上流・下流へ辿れる成果物と関係を強調する
4. それ以外を30%の不透明度にする
5. 現在のプロセス境界に達した場合は、対応する `ProcessHandoff` を「別プロセスへ続く」項目として右パネルへ表示する
6. 右パネルに到達順の一覧を表示する

### 8.3 探索対象

保証連鎖では、次の `semanticType` を優先して辿る。

- `derives-from`
- `justifies`
- `mitigates`
- `monitors`

`semanticType` が付いていない場合は、`prepType = input` の向きを利用する。

`ProcessHandoff` を介して別プロセスへ続く場合も探索結果には含めるが、別プロセスの成果物を現在のキャンバスへ重ねて表示しない。ユーザが引継ぎ先をクリックしたときに、そのプロセス詳細へ移動して同じ探索状態を継続する。

### 8.4 出力

右パネルに次を表示する。

- 上流成果物
- 下流成果物
- 通過した関係
- 最終成果物まで到達できたか
- 経路上の高リスク要素
- 別プロセスへ続く引継ぎ先

## 9. 変更影響表示

### 9.1 目的

要求、制約、リスク、評価基準が変更されたとき、再確認すべき成果物を特定する。

根拠：

- `02-prep_research_reframed_plan.md`, RQ3, §14.5.3：変更影響追跡性と変更シナリオ

### 9.2 操作

1. ユーザが変更元の成果物を選択する
2. 「変更影響」を押す
3. `requires-revalidation-of` を優先して下流探索する
4. 明示的な再検証関係がない場合は、入力関係の下流を「推定影響」として表示する
5. 最終成果物から `ProcessHandoff` がある場合は、引継ぎ先プロセスを「プロセス間影響」として表示する

### 9.3 表示区分

| 区分 | 表示 |
|---|---|
| 明示的影響 | 赤 |
| 推定影響 | 橙 |
| プロセス間影響 | 紫。右パネルから引継ぎ先プロセスを開く |
| 影響なし | 薄い灰色 |

明示的影響、推定影響、プロセス間影響を混同しない。別プロセスの詳細ノードは現在のキャンバスへ直接描かない。

## 11. 技術構成

### 11.1 採用技術

| 用途 | 技術 |
|---|---|
| ビルド | Vite |
| UI | React + TypeScript |
| グラフ編集 | `@xyflow/react` |
| 状態管理 | Zustand |
| スキーマ検証 | Zod |
| プロセス詳細レイアウト | 独自のレーン×列グリッド |
| 鳥瞰図の自動整列 | `@dagrejs/dagre` |
| アイコン | `lucide-react` |
| 画像出力 | `html-to-image` |
| テスト | Vitest + React Testing Library |
| E2E | Playwright |

React Flowは、ドラッグ、ズーム、パン、選択、要素追加・削除、カスタムノード、カスタムエッジなど、ノードベースエディタに必要な基本機能を提供するため、本MVPに適している。機能の範囲は [React Flow公式サイト](https://reactflow.dev/) と [公式Examples](https://reactflow.dev/examples) を根拠とする。

タッチパッドの二本指ドラッグは、React Flowのデザインツール型ビューポート設定に合わせて実装する。[React Flow公式のPanning and Zooming](https://reactflow.dev/learn/concepts/the-viewport) が示す `panOnScroll` を有効にし、[ReactFlowコンポーネントAPI](https://reactflow.dev/api-reference/react-flow) の `panOnScrollMode="free"`、`panOnScrollSpeed`、`zoomOnPinch`、`preventScrolling` を利用する。通常の二本指ドラッグは縦横パン、ピンチと修飾キー付きスクロールはズームとする。

8方向の接続点は、各 `<Handle>` に一意なIDを付け、React FlowのEdgeが持つ `sourceHandle` と `targetHandle` へ対応付ける。[React Flow公式Handles](https://reactflow.dev/learn/customization/handles) と [Edge型](https://reactflow.dev/api-reference/types/edge) に従う。四隅のHandleはCSSで位置を調整し、入力・出力の両方に使えるよう `connectionMode="Loose"` とする。

サブプロセス範囲ボックスをReact Flowのカスタムノードとして描画する実装では、公式の [`NodeResizeControl`](https://reactflow.dev/api-reference/components/node-resize-control) を右辺、下辺、右下角へ限定して使用してよい。レイアウト層のDOMとして描画する場合は同じ操作仕様をPointer Eventsで実装する。いずれの場合も、リサイズ結果はReact Flow内部状態だけでなく `SubprocessColumnLayout.width` と `height` へ反映する。

成果物間関係の初期線種は、直交グリッドと相性のよい `smoothstep` とする。[React Flow公式Edge Types](https://reactflow.dev/examples/edges/edge-types)

アクターレーンとサブプロセス列は、Dagreに自由配置させない。レーン順序、列順序、保存済みサイズからセル矩形を計算し、そのセル内だけ成果物を移動できる独自レイアウトを実装する。Dagreは鳥瞰図の二重丸の自動整列に限定する。

ViteはReactとTypeScriptを用いた小規模な静的Webアプリを構成できる。導入方法とビルド方法は [Vite公式ガイド](https://vite.dev/guide/) と [Static Deployガイド](https://vite.dev/guide/static-deploy) に従う。

画像出力はReact Flow公式例が使用する `html-to-image` を用いる。公式例では新しい版で出力できない既知問題が示されているため、初回実装では公式例に合わせて `html-to-image@1.11.11` を固定する。[React Flow公式Download Image例](https://reactflow.dev/examples/misc/download-image)

## 16. 実装時の判断ルール

1. 資料にない独自記号を勝手に追加しない
2. PReP標準の `prepType` と研究用の `semanticType` を分離する
3. タスクフローを中心にしない
4. 保存データの正は `PrepModelFile` とする
5. React Flow固有のデータをドメイン層へ漏らさない
6. 明示的関係と推定関係をUI上で区別する
7. 入力不足はエラーまたは警告として見せ、暗黙に補完しない
8. テンプレートは通常のモデルデータとして持ち、専用コードを増やさない
9. 研究用サンプルの文言は日本語で用意する
10. READMEに起動方法、操作方法、保存形式を記載する
11. サブプロセスを新しいドメイン型として重複実装せず、`PrepProcess.parentProcessId` で表現する
12. プロセス詳細では `activeProcessId` と直下サブプロセス以外の成果物を描画しない
13. アクター横レーンとサブプロセス縦列を見た目だけの背景にせず、責任と所属のデータへ対応付ける
14. 各成果物の主責任は `responsibleActorId` で1人に定める
15. 成果物関係の接続点は `sourceAnchor` と `targetAnchor` に保存し、表示時の自動計算だけにしない
16. プロセス間関係は `ProcessHandoff`、プロセス内の成果物関係は `PrepRelation` として分離する
17. 鳥瞰図ではトップレベルプロセスを二重丸、外部プロセスを点線の二重丸で表示する
18. 深いサブプロセスを親画面へ重ねず、そのサブプロセスを開いて表示する
19. 既存のv1.0.0、v1.1.0およびv1.2.0データを破壊せず、読込時の移行関数を単体テストする
20. プロセス詳細と鳥瞰図で二本指パンの設定を共通化し、通常スクロールは自由方向パン、ピンチと修飾キー付きスクロールはズームとして扱う
21. パン操作はビューポートだけを更新し、成果物の配置、責任、所属、選択状態を変更しない
22. 標準のReact Flow propsで実現できる場合は独自の `wheel` ハンドラを作らない
23. サブプロセス範囲ボックスのリサイズは表示だけで終わらせず、`SubprocessColumnLayout.width` と `height` へ保存する
24. リサイズによって成果物を自動移動、縮小、別サブプロセスへ再所属させない
25. リサイズ中はパンや成果物ドラッグよりリサイズ操作を優先する
